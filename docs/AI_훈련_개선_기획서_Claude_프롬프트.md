# 미끼주의보 AI 훈련 개선 기획서 및 Claude Code 프롬프트

## 1. 작업 목표

사용자의 대화 맥락과 실제 행동을 바탕으로 훈련을 적절히 종료하고, 실제 대화에 근거한 리포트를 제공한다. 사용자가 장난을 치거나 일부러 속는 척하는 상황도 다루며, 기존 대화 엔진에 녹음형 음성 인식과 TTS를 연결한다.

### 이번 작업 범위

1. 대화 맥락을 반영한 종료 판단
2. 종료 이유 및 대화 결과를 리포트에 전달
3. 실제 대화와 행동을 근거로 한 피드백 제공
4. 새 훈련 시작 시 대화·판정 상태 초기화
5. 장난 또는 일부러 속는 척하는 상황 처리
6. 녹음형 음성 인식과 TTS 연결

## 2. 현재 파악된 상태

다음은 전달받은 코드 설명이며, 실제 구현 전 Claude Code가 확인한다.

- 대화 생성과 발화 판정은 공통 AI 모듈 `ai.ts`를 사용한다.
- 현재 화면은 DB에 저장하지 않는 `practice-chat` 경로에 연결되어 있다.
- 대화 중 Gemini가 판정한 사용자 의도가 응답이나 리포트에 유지되지 않는다.
- 종료 여부는 있지만 종료 이유를 화면에서 구분할 수 없다.
- 연습 종료 후 실제 대화에 기반한 리포트가 표시되지 않으며, 기존 리포트 화면은 하드코딩된 사례를 표시한다.
- DB 기반 세션 경로와 로컬 실험 경로에는 별도의 결과 판정 로직이 있다.

실제 사용자가 이용하는 `practice-chat` 및 연결된 화면을 우선한다. 기존 DB 기반 경로는 구조와 영향을 확인한 뒤 호환성을 유지한다.

## 3. 종료 판단

### 3.1 기본 원칙

- AI는 대화 맥락을 보고 사용자 발화의 의미와 종료 필요성을 판단한다.
- 프로그램은 실제 행동 이벤트, 종료 조건과 최대 대화 횟수를 관리한다.
- 사용자가 말한 내용과 화면에서 발생한 실제 행동을 구분한다.
- 근거가 모호하면 의도나 행동을 단정하지 않는다.
- 사용자가 중단하면 AI 응답을 기다리지 않고 즉시 중단한다.
- 종료 후 추가 대화나 중복 종료 처리가 발생하지 않도록 한다.

### 3.2 종료 이유 초안

실제 코드에 정의된 타입과 동작을 확인하고 필요한 범위에서 확장한다.

| 종료 이유 | 예시 | 결과에 남길 내용 |
| --- | --- | --- |
| 요청 거절 | “링크는 안 누를게”, “돈 안 보내” | 거절 발화 |
| 직접 확인 의사 | “원래 번호로 전화해 볼게” | 확인 의사. 실제 확인 완료로 간주하지 않음 |
| 직접 확인했다고 말함 | “딸이 지금 내 옆에 있는데?” | 대화에서 확인했다고 말한 내용 |
| 요청 수락 의사 | “수리비 보내줄게” | 요청에 응하겠다는 발화. 실제 송금과 구분 |
| 행동했다고 말함 | “이미 보냈어”, “링크 눌렀어” | 행동했다고 말한 사실. 실제 이벤트와 분리 |
| 모의 행동 발생 | 모의 링크 클릭 또는 모의 송금 이벤트 | 시스템이 실제로 기록한 이벤트 |
| 상대가 대화 중단 | 반복되는 반응에 상대가 의심하고 물러남 | 상대의 종료 연출과 근거 대화 |
| 사용자 중단 | “그만할래” 또는 중단 버튼 | 중단 사실 |
| 판단 보류 | 대화가 모호하거나 최대 턴에 도달 | 판단이 어려웠던 이유와 관찰된 사실 |

종료 연출과 사용자 평가를 분리한다. 상대가 물러났다는 이유만으로 사용자가 사기를 알아챘다거나 실제 링크를 눌렀다고 판단하지 않는다.

### 3.3 반복 대화 방지

- 같은 요구와 답변이 반복되는 상황을 처리한다.
- 비슷한 답변의 반복도 대화 맥락을 고려한다.
- 반복이 계속되면 상대가 대화를 마무리하거나 훈련이 종료될 수 있다.
- 최대 턴은 서버 측에서도 관리한다.
- 최대 턴과 반복 기준은 현재 구현을 확인한 뒤 조정 가능하게 둔다.

## 4. 장난 및 속는 척하는 상황

### 4.1 처리 원칙

사용자가 “눌렀어”, “돈 보냈어”라고 말하거나 상대를 놀리는 상황을 고려한다. AI가 실제 의도를 확실히 알 수 없으므로 다음을 구분한다.

1. 사용자 발화: 무엇이라고 말했는가?
2. 실제 이벤트: 모의 링크 클릭 또는 모의 송금이 기록됐는가?
3. AI 해석: 대화 맥락상 장난이나 의심의 가능성이 있는가?

AI의 해석은 추정이며 거짓말이나 장난을 확정하는 근거로 사용하지 않는다. 모의 송금 이벤트가 없다면 실제 송금 여부를 판단할 수 없다.

### 4.2 처리 예시

| 상황 | 처리 방향 |
| --- | --- |
| 링크를 보내기 전 “눌렀어”라고 말함 | 링크가 아직 없었다는 맥락을 고려 |
| 링크가 표시된 뒤 “눌렀어”라고 말했지만 클릭 이벤트가 없음 | 접속했다고 말한 것과 실제 클릭이 기록되지 않은 것을 분리 |
| “보냈어”라고 말함 | 송금했다고 말한 사실을 기록. 이벤트가 없다면 실제 여부를 확정하지 않음 |
| “사기꾼이지? 일부러 놀린 거야” | 상황에 맞게 상대가 의심받았다고 반응하고 물러날 수 있음 |
| 모호한 답변이 한 번 나옴 | 곧바로 장난으로 단정하지 않고 맥락 확인 |
| 비슷한 답변이 반복됨 | 재확인 후 상대가 대화를 중단하거나 반복 제한으로 종료 |

상대는 맥락에 따라 짧게 재확인한 뒤 대화를 정리할 수 있다. 리포트에는 관찰된 발언과 이벤트를 적고, 사용자가 의도적으로 거짓말했다고 단정하지 않는다.

## 5. 리포트와 피드백

### 5.1 리포트에 전달할 정보

| 항목 | 내용 |
| --- | --- |
| 훈련 식별 정보 | 시나리오 또는 미션 |
| 대화 내용 | 사용자와 상대방의 실제 메시지 |
| 사용자 발화 분석 | 의도, 근거 발화, 불확실 여부 |
| 실제 행동 이벤트 | 모의 링크 클릭 등 시스템이 확인한 행동 |
| 종료 이유 | 거절, 직접 확인 의사, 중단, 판단 보류 등 |
| 피드백 | 관찰된 대응과 다음에 취할 수 있는 행동 |

DB에 저장하지 않는 연습 경로에서도 정보가 리포트 화면까지 유지되어야 한다. 전달 방식은 현재 프로젝트 구조를 보고 정한다. 리포트 표시를 위한 임시 유지와 DB 영구 저장은 별개다. 새로고침 및 직접 URL 접근 시 동작을 명시하고, 대화 전문이나 민감한 내용을 URL 쿼리에 그대로 넣지 않는다.

### 5.2 피드백 원칙과 예시

- 실제 발화와 확인된 행동을 근거로 한다.
- 발화와 이벤트, 확인 의사와 확인 완료를 구분한다.
- 사용자의 의도나 평소 능력을 단정하거나 비난하지 않는다.
- 구체적인 다음 행동을 쉬운 문장으로 제안한다.
- AI 피드백 실패 시 기록된 종료 이유에 맞는 기본 피드백을 제공한다.
- 근거가 없는 행동을 생성하지 않는다.

**직접 확인 의사:** “원래 번호로 전화해 볼게”라고 말씀하셨어요. 상대가 보내 준 정보와 별도로 평소 알고 있던 연락처로 확인하려는 대응이 좋았어요.

**모의 링크 클릭:** 이번 훈련에서는 상대가 보낸 모의 링크를 열었어요. 실제 상황에서는 링크를 열기 전 평소 알고 있던 연락처로 가족에게 직접 확인해 보세요.

**클릭했다고 말했지만 이벤트 없음:** 대화에서는 링크를 눌렀다고 말씀하셨지만, 훈련 화면에서 모의 링크 클릭은 기록되지 않았어요. 의심스러운 링크는 열기 전 가족에게 직접 확인해 보세요.

**판단 보류:** 이번 대화만으로는 어떤 방법으로 확인하실지 판단하기 어려웠어요. 급한 요청을 받으면 잠시 멈추고, 평소 알고 있던 연락처로 확인해 보세요.

## 6. 새 훈련 시작 시 초기화

다시 연습하기를 선택하면 새 훈련으로 시작한다. 이전 대화, 사용자 발화 분석, 턴 수 및 반복 횟수, 종료 여부와 종료 이유, 행동 이벤트, 이전 리포트 임시 데이터, 녹음·음성 재생 상태 및 진행 중인 요청을 정리한다.

이전 요청의 늦은 응답이 새 훈련에 반영되지 않게 한다. 별명이나 미션·훈련 방식 선택 유지 여부는 기존 UX와 팀 기획을 확인해 결정한다.

## 7. 음성 인식 및 TTS

### 7.1 적용 방향

사용자 음성 → 녹음 → 음성 인식으로 텍스트 변환 → 사용자가 확인·수정 → 기존 대화 엔진에 전달 → Gemini 응답 생성 → TTS로 응답 읽기.

이번에는 버튼을 눌러 말하고 녹음 후 인식하는 방식을 우선한다. 실시간 양방향 음성 대화는 이후 확장한다.

### 7.2 음성 인식

우선 검토 모델은 `gemini-3.5-transcribe`다. 한국어 음성을 변환하고 사용자가 결과를 확인·수정한 뒤 기존 대화 엔진에 전송한다. 확인 전 인식 결과만으로 종료하거나 위험 행동으로 확정하지 않는다. 실패 시 다시 말하거나 직접 입력할 수 있게 한다.

구현 시점의 공식 문서, 프로젝트 SDK, 모델 접근 가능 여부, 비용과 데이터 처리 조건을 확인한다.

### 7.3 TTS

현재 프로젝트의 음성 출력을 먼저 확인한다. 기존 브라우저 음성 읽기를 사용할 수 있으면 먼저 평가하고, 품질이나 지원이 부족하면 별도 TTS API를 비교한다. 실제 가족의 목소리를 복제하지 않는 가상의 훈련용 목소리로 시작한다. 통화 종료·훈련 중단·새 훈련 시작 시 재생을 멈춘다.

음성 인식은 사용자 음성을 글로 바꾸고, TTS는 AI의 글을 소리로 읽는다. 오류와 대체 입력·출력을 각각 처리한다.

### 7.4 음성 UX·데이터

- 마이크 권한 요청·거부, 녹음 시작·종료 표시, 녹음 실패와 빈 음성 처리
- 인식 실패·재시도·문장 수정 및 직접 텍스트 입력 대체
- 음성 재생 실패·음소거·중단, 느린 발화와 잠깐의 침묵 고려
- API 키는 브라우저나 저장소에 노출하지 않고 서버 구조에 맞게 관리
- 초기 테스트는 가상 문장만 사용. 녹음 파일은 필요 없이 장기 보관하지 않음
- 실제 사용자 음성의 처리·보관·삭제와 고지는 팀에서 협의

- [ ] AI 응답을 음성으로 듣고 중단할 수 있다.
- [ ] 음성 입력이 기존 종료 판단 및 리포트에 연결된다.

기능 요구사항으로 사용해줘. 문서와 현재 코드에 차이가 있으면
실제 동작을 확인하고 중요한 기획상 차이는 최종 보고에 명시해줘.

우선 확인할 흐름:
- 현재 화면이 호출하는 practice-chat 경로
- 공통 AI 모듈의 대화 생성과 사용자 발화 판정
- 훈련 종료 조건과 최대 턴 처리
- 연습 종료 후 리포트 화면으로 전달되는 데이터
- 기존 session-end, chat-turn, 로컬 실험 경로의 관계
- 현재 녹음, 음성 인식, TTS 관련 코드
- 기존 테스트와 실행 명령

구현 목표 1: 종료 판단
- 대화 맥락을 바탕으로 요청 거절, 직접 확인 의사,
  요청 수락 의사, 사용자의 중단, 판단 보류 등을 구분한다.
- “지금 내 딸 옆에 있는데 수리비 필요 없다는데?”처럼
  대화에서 가족에게 직접 확인했다고 말한 상황도 처리한다.
- 사용자의 발화와 시스템에 기록된 실제 행동 이벤트를 분리한다.
- 사용자가 “링크 눌렀어”라고 말한 것만으로
  실제 모의 링크 클릭이 발생했다고 판단하지 않는다.
- 클릭이나 모의 송금 이벤트를 확인할 수 없는 경우
  행동이 실제로 일어났는지 단정하지 않는다.
- 사용자의 명시적인 중단 요청은 즉시 처리한다.
- 반복 대화 및 최대 턴을 서버 측에서도 처리해
  채팅이 무한히 이어지지 않도록 한다.
- 종료 이유와 판정 근거를 리포트에 전달할 수 있도록 한다.

구현 목표 2: 장난 및 속는 척하는 상황
- 사용자 발화, 실제 모의 행동 이벤트, AI의 맥락 해석을 구분한다.
- 사용자가 행동했다고 말했지만 이벤트가 없거나,
  상대를 의심하는 발언이 반복되는 경우 상대가 재확인하거나
  대화를 정리하고 물러나는 흐름을 지원한다.
- 사용자가 실수했을 가능성도 있으므로 한 번의 모호한 발화만으로
  장난 또는 거짓말이라고 단정하지 않는다.
- 상대가 대화를 중단한 연출과 사용자의 행동 평가는 별도로 기록한다.

구현 목표 3: 종료 후 리포트
- 현재 사용자가 실제로 사용하는 연습 경로를 우선 연결한다.
- 하드코딩된 사례 대신 실제 대화, 종료 이유,
  관찰된 이벤트와 판정 근거를 리포트에 표시한다.
- 대화별로 구체적인 피드백을 제공한다.
- AI 피드백이 실패하거나 근거가 불충분하면
  실제 기록에 맞는 기본 피드백 또는 판단 보류를 표시한다.
- DB를 사용하지 않는 연습 경로에서도 리포트까지 정보가 전달되도록 한다.
- 전달 방식과 새로고침 시 동작은 현재 프로젝트 구조에 맞게 정한다.
- 대화 전문이나 민감한 데이터를 URL 쿼리에 넣지 않는다.
- 기존 DB 기반 세션과 로컬 실험 경로가 있다면
  호환성을 깨지 않도록 영향을 확인한다.

구현 목표 4: 새 훈련 초기화
- 다시 연습할 때 대화, 판정, 턴 수, 행동 이벤트,
  종료 이유, 리포트 임시 상태를 초기화한다.
- 이전 요청의 늦은 응답이 새 훈련을 덮어쓰지 않도록 한다.
- 녹음과 TTS 재생도 정리한다.
- 별명과 미션 선택 유지 여부는 현재 UX를 확인하고
  임의로 기존 동작을 바꾸지 않는다.

구현 목표 5: 음성 입력과 TTS
- 기존 음성 관련 코드를 먼저 확인하고 재사용 가능성을 평가한다.
- 음성 입력은 녹음 후 텍스트로 변환하는 방식을 우선한다.
- Gemini 3.5 Transcribe를 우선 검토하되,
  현재 공식 문서, SDK, 모델 접근 가능 여부를 확인한다.
- 사용자가 인식된 문장을 확인하고 수정한 뒤 전송하도록 한다.
- 확인 전 인식 결과만으로 훈련을 자동 종료하지 않는다.
- API 키를 브라우저나 저장소에 노출하지 않고,
  프로젝트의 서버 및 비밀값 관리 방식에 맞춘다.
- TTS는 기존 구현을 먼저 활용하고, 부족한 부분을 보완한다.
- 마이크 권한 거부, 빈 녹음, 인식 실패, 재시도,
  텍스트 입력 대체, 재생 중단을 처리한다.
- 실시간 스트리밍 음성 대화와 실제 가족 목소리 복제는 구현하지 않는다.

검증:
- 관련 자동 테스트를 기존 프로젝트 방식에 맞춰 추가하거나 수정한다.
- 종료 이유별 사례, 클릭 발화와 실제 이벤트의 차이,
  반복 대화, 리포트 근거, 새 훈련 초기화를 검증한다.
- 음성 API 키나 마이크를 사용할 수 없다면
  테스트 가능한 부분을 검증하고 미검증 항목을 명시한다.
- 실제 개인정보 대신 가상의 대화와 음성을 사용한다.
- 관련 테스트와 프로젝트가 요구하는 검사를 실행한다.

문서:
- API 요청·응답이나 설정이 바뀌면 실제 구현에 맞게
  관련 계약 문서와 인수인계 문서를 갱신한다.
- 새 환경 변수, 실행 방법, 모델 설정, 테스트 방법,
  음성 기능의 제약을 기록한다.
- 확인하지 않은 내용을 완료된 것으로 표시하지 않는다.

작업을 마치면 다음을 알려줘.
1. 실제 코드에서 확인한 기존 문제와 수정 내용
2. 변경한 주요 파일
3. 실행한 테스트와 결과
4. API 키·마이크·외부 서비스가 없어 확인하지 못한 항목
5. 팀과 추가로 결정해야 할 UI 또는 데이터 전달 사항
